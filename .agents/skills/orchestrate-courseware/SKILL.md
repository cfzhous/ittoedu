# 编排互动课件

目标是得到两份足够支撑制作、仍保留教师自由度的当前 Markdown；聊天记录不是交付真相。

## 原则

1. 直接读取教师提供的文件和材料，不要求教师复述已经写明的内容。
2. 材料越完整，提问越少；只有主题时可以多轮追问，不设置问题总数上限。
3. 一轮只集中处理最影响结果的少量问题。可以先给有依据的草案，再请教师纠偏。
4. 不预设课型、教学法、场景数量、页面结构、互动比例、视觉风格或固定模板。
5. 教学策划与教学呈现都可以提问；只保留两次制作前确认，材料闭合时可以合并。
6. 不建立 Hash、签名、审批状态机、候选等级、固定字段清单或额外合同文件。
7. 本 Skill 不选择 Native、Runtime、Component，不写代码、Project 或导出物。

## 1. 诊断输入

读取主题、材料路径、既有两份 Markdown 和用户本轮补充。区分：

- 已由材料确定的事实；
- 可以合理起草、但需要教师复核的判断；
- 会改变教学目标、内容正确性、课堂实施或评价方式的缺口。

只追问第三类。涉及版本、来源或学科事实且不能从材料确定时，先核查权威来源；不要把检索结果伪装成教师选择。

## 2. 形成教学策划

创建或修订 `01-teaching-plan.md`。自由组织内容，使另一位教师脱离聊天也能理解：教谁、为何教、教什么、怎样知道学会、主要困难、课堂条件、材料依据和仍存在的假设。

按输入缺口渐进提问。教师可以直接在 Markdown 中修改；每次继续前重读当前文件，以文件为准。

完成一份可评审草案后停止一次，简要标出关键判断、材料缺口和待教师确认处，请教师确认或直接修改。未确认前不进入工程构建。

## 3. 形成教学呈现脚本

策划确认后创建或修订 `02-presentation-script.md`。同样自由组织，但必须让 Builder 无需猜测即可还原教师可感知的体验，包括：

- 内容如何展开，以及必要的逐字文本、公式、数据、答案、解释或素材引用；
- 是否分场景及如何分，教师和学生分别看到什么、做什么；
- 交互前、交互中、结果、错误、重试、揭示、返回和重播等确有需要的状态；
- 教师控制、课堂节奏、评价边界、静态输出差异和无障碍要求；
- 明确不能静默改变的教学与视觉取舍。

这些是教学呈现设计，不是技术实现说明。不要写节点类型、API、Schema 或组件选型。

完成后停止第二次，展示最重要的体验取舍并请教师确认。若策划与脚本由完整材料一次形成，可合并为一次明确确认。

## 4. 交给干净 Builder

确认后使用 `$build-courseware-project`。优先启动不继承本轮长聊天的干净 Build Coordinator；只传：

- 两份当前 Markdown 的路径；
- 原始材料路径；
- 编辑器/Agent Kit/当前能力入口；
- 用户仍然有效的额外约束。

不要传递旧草案、被否决方案、冗长讨论摘要或本 Skill 的内部推断。若不能启动干净上下文，也要重新从两份文件开始构建，而不是依赖聊天记忆。

Builder 发现真正的教学内容缺口或需要改变教师已确认的体验时，返回本 Skill 修订相应文件；纯技术分解留在 Builder。
