# AI 互动课件通用创作编排规范

> 适用范围：跨学科、当前已实现的 PPT 兼容固定画布课件
>
> 适用版本：Editor 1.7.0 / Project V7
>
> 状态：当前 AI 创作流程的前置强制规范
>
> 同步基线：2026-08-06

本文规定从教学需求进入到成品接受之间的设计编排、人类决策、阶段产物和质量门禁。仓库中的 [orchestrate-courseware Skill](../.agents/skills/orchestrate-courseware/SKILL.md) 负责执行并持久化本文流程；本文继续作为权威规范与审阅依据。它不替代 [Project V7 创作与接入规范](AI_COURSEWARE_AUTHORING.md)：本文负责先把“为什么教、准确教什么、学生看到什么和做什么”确认清楚，后者只负责把已确认方案可靠实现为当前编辑器可打开、可轻改、可预览和可导出的工程。

Editor 1.x 没有内置模型调用、自动弹框或 AI patch。本流程由编辑器外部的 AI 创作会话执行；需要人类决策时必须先生成宿主无关的 `DecisionPrompt`，再由宿主以结构化选择控件呈现。宿主不具备该能力或当前会话模式不允许结构化选择时，流程进入 `decision-blocked`，不得静默降级为普通文本提问，也不得把本文描述成人工智能已经集成进 Editor 1.x。

当前生产能力只有固定 1280×720、可导出 PPTX 的 Project V7 课件。其他尚未实现的创作表面不属于本文生成协议，也不得由 AI 伪造 Project 字段或成品能力。

## 1. 编排层的职责

通用创作编排层负责：

1. 汇集用户材料、权威来源和可用的学科上下文；
2. 判断教学设计是否完整、是否存在高影响不确定项；
3. 只把真正需要人类决定的问题组织成少量、清晰的选项；
4. 生成或整理可批准的教学设计；
5. 把教学设计展开为完整、可核验的教学内容规格，冻结题面、材料、答案、推理、难度、容量和揭示边界；
6. 把已批准教学设计和教学内容规格转换为可逐项验收的教学呈现脚本；
7. 在必要时提供视觉方向、关键帧或核心互动样片供人类确认；
8. 在内部完成 Project V7 技术路径设计，不把实现细节推给普通用户；
9. 组织实现、真实播放、兼容导出和结果验收；
10. 只有在人类接受成品后，才登记参考案例和复用候选。

编排层不负责：

- 用技术实现替代缺失的教学设计；
- 把所有问题都交回用户；
- 让既有模板、组件或素材反向决定教学目标；
- 在设计未批准时直接批量生成最终工程；
- 把管线通过写成视觉、教学或成品已接受；
- 为尚未实现的编辑器能力编造数据结构或交付承诺。

## 2. 不可颠倒的四个层次

任何非简单修改都必须按以下顺序收敛：

```text
教学设计（Why / What）
  → 为什么教、教到什么边界、如何证明学会

教学内容规格（Exact content）
  → 完整题面/材料、答案、推理、错误、难度、容量与揭示规则

教学呈现（What happens）
  → 学生看到什么、做什么、得到什么反馈

技术实现（How）
  → 用哪些节点、状态、规则、运行时、组件和素材实现
```

不得在教学设计尚不明确时先选择题型、页面模板或组件；不得让呈现脚本或实现阶段临时编写本应在教学内容规格中冻结的题目、答案和难度；不得把 Project Schema 字段清单当作教学呈现脚本；不得因已有组件方便而修改已经批准的学习目标和证据链。

## 3. 阶段状态与人类门禁

创作会话至少使用以下逻辑状态。状态可由外部 AI 会话记录，不要求写入 Project V7。

| 状态 | 含义 | 人类可见产物 | 允许进入下一阶段的条件 |
| --- | --- | --- | --- |
| `intake` | 正在接收材料 | 输入摘要 | 输入来源和任务目标已登记 |
| `context-ready` | 上下文已汇集 | 权威来源、缺失项和冲突摘要 | 来源优先级明确 |
| `awaiting-decisions` | 存在高影响不确定项 | 结构化选项 | 阻断项已回答或用户批准推荐默认值 |
| `decision-blocked` | 当前宿主无法可靠呈现结构化选择 | 能力缺口和恢复方式 | 切换到支持结构化选择的会话模式后重新呈现同一 `DecisionPrompt` |
| `teaching-design-review` | 教学设计待确认 | 教学设计稿 | 目标、证据链、内容边界和节奏获批准 |
| `content-spec-review` | 教学内容规格待确认 | 完整内容、答案、难度与容量清单 | 权威内容、推理、错误边界、揭示规则和时长获批准 |
| `presentation-script-review` | 教学呈现待确认 | 逐节拍呈现脚本 | 所有核心操作、反馈、分支和结束状态获批准 |
| `visual-review` | 视觉方向待确认 | 视觉说明、关键帧或样片 | 高风险视觉与核心互动方向获批准 |
| `implementation-ready` | 可以设计实现 | 确认摘要，不展示普通技术细节 | 必需批准记录完整 |
| `building` | 正在实现 | 简短进度与已发现的重大取舍 | 未出现需要重新批准的产品变化 |
| `outcome-review` | 成品待验收 | HTML、截图、录屏、导出与差异说明 | 用户完成结果审阅 |
| `accepted` | 成品已接受 | 接受记录与剩余风险 | 用户明确接受或任务定义的批准人确认 |
| `reuse-review` | 评估复用价值 | 案例卡与候选模式 | 通过复用治理，不自动晋升模板/组件 |

禁止从 `intake` 直接跳到 `building`，除非任务只是对已接受课件做不改变教学设计和呈现语义的小修。任何实现中出现的教学、视觉或交互重大变化都必须退回对应审阅状态。

## 4. 上下文汇集与权威顺序

### 4.1 可接收的上下文

创作会话可以接收：

- 用户上传或粘贴的教学设计、教案、课标、教材节选和文案；
- 用户指定的图片、视频、声音、模型和品牌素材；
- 经批准的学科知识资料；
- 经批准的学科创作说明；
- 有来源和许可证记录的素材库条目；
- 已接受课例、候选模板和已发布组件；
- 当前编辑器、Project V7、运行时和组件规范。

本文不规定未来知识库或素材库的存储、检索和联网机制。上下文可以通过附件、本地文件或其他受控方式提供；AI 只能使用本次会话实际获得的内容，不得声称加载了不存在的库。

### 4.2 决策优先级

发生冲突时按以下顺序处理：

1. 当前平台的安全、Schema、离线和可信代码硬约束；
2. 用户明确要求及用户指定的权威来源；
3. 本次会话已经批准的教学设计、教学内容规格、呈现脚本和决策记录；
4. 经批准的学科知识与学科创作说明；
5. 本通用规范中的创作默认值；
6. 相似课例、模板、组件和素材建议。

若用户材料与经批准的学科知识发生事实、安全或课程标准冲突，AI 不得静默选择一方，应说明冲突、影响和建议，由人类决定或补充权威来源。平台硬约束不能通过选项被绕过。

### 4.3 上下文清单

非简单项目应在内部维护上下文清单，至少记录：

```ts
interface AuthoringContextEntry {
  id: string
  role:
    | 'user-brief'
    | 'authoritative-source'
    | 'subject-knowledge'
    | 'subject-authoring-guide'
    | 'approved-asset'
    | 'reference-case'
    | 'template-candidate'
    | 'component'
    | 'platform-spec'
  title: string
  version?: string
  source?: string
  authority: 'hard-constraint' | 'authoritative' | 'guidance' | 'reference'
  notes?: string
}
```

这只是编排记录格式，不写入 Project V7，也不表示编辑器已经实现上下文管理界面。

## 5. 输入就绪诊断

收到材料后先分类，不立即生成工程。

### 5.1 四种输入路径

| 路径 | 输入情况 | 默认处理 |
| --- | --- | --- |
| A. 已批准教学设计 | 目标、证据、流程和内容完整 | 保真整理，检查冲突并形成可批准的教学内容规格后进入呈现脚本 |
| B. 部分教学设计 | 有主题和内容，但目标、证据或流程缺失 | 补齐候选方案并询问高影响选择 |
| C. 只有主题/素材 | 缺少教学设计 | 先生成 2–3 个有实质差异的教学设计方向供选择 |
| D. 改编既有课件 | 有旧课件、模板或参考案例 | 先区分必须保留、可以改动和明确淘汰的内容 |

不得把 A 路径中的明确要求擅自重写成 AI 更熟悉的通用课程；不得把 C 路径伪装成“设计已经完整”后直接实现。

### 5.2 就绪检查

在进入教学设计审阅前，至少确认：

- 学习者年龄、年级、先修知识和使用语言；
- 使用场景：教师投影、学生自学、课堂练习或混合使用；
- 可观察、可评价的学习目标；
- 核心内容、边界和不能改动的表述；
- 常见误概念、困难或错误路径；
- 学习证据：学生完成什么行为才算达到目标；
- 预计时长、课堂节奏和教师是否需要控制进程；
- 必须使用、禁止使用或尚缺失的素材；
- 是否要求分支、失败反馈、重试、声音或关键动效；
- HTML 成品和 PPTX/PDF 兼容交付的优先级及静态化接受度；
- 事实、安全、版权和授权风险。

缺少低影响信息时可以使用明确默认值；缺少会改变学习目标、证据链、关键呈现或交付结果的信息时必须进入 `awaiting-decisions`。

## 6. 高影响不确定项与结构化选择

### 6.1 必须询问的事项

以下不确定项通常需要人类选择：

- 学习目标或核心误概念存在多种合理解释；
- 教师主导演示与学生自主探索会形成不同课件；
- 概念解释、技能训练、诊断和考核之间的主目标不明确；
- 是否允许失败、分支、重试、开放答案或教师揭示；
- 视觉方向、真实实验、抽象模型或情境故事会显著改变体验；
- 必需素材缺失，生成、占位或等待上传会产生不同结果；
- HTML 效果与 PPTX 对象级可编辑性存在重大取舍；
- 需要付费工具、特殊许可证、在线服务或高性能设备；
- 用户材料与学科知识、事实或安全要求发生冲突。

### 6.2 不应询问普通用户的事项

以下内容默认由 AI 在技术设计阶段决定：

- 使用 `scene.interactions` 还是运行时事件；
- 使用 DOM、Phaser、Canvas 或 WebGL；
- 节点 ID、状态 ID、组件包 ID 和 `renderMode`；
- Tween 参数、资源加载和销毁细节；
- Project V7 字段组织；
- 测试夹具和构建脚本结构。

只有这些技术选择会改变已经批准的画面、互动、成本、授权、性能或兼容导出时，才把“用户可感知的取舍”重新呈现给人类，不要求用户替 AI 选择底层技术。

### 6.3 选项设计规则

每轮优先提出 1–3 个最有决策价值的问题：

- 选项互斥且含义清楚；
- 推荐项排在前面并说明推荐原因；
- 每项用一句话说明对成品的实际影响；
- 不使用“专业/高级/更好”等无信息标签；
- 不把同一问题拆成多轮追问；
- 能从权威材料确定的事实不再询问；
- 如果没有安全的默认值，必须等待回答；
- 如果默认值不会实质改变结果，可以继续并记入假设清单。

决策问题先抽象为宿主无关的 `DecisionPrompt`，再映射到宿主选择控件：

```ts
interface DecisionPrompt {
  schemaVersion: 1
  id: string
  stage:
    | 'intake'
    | 'teaching-design-review'
    | 'content-spec-review'
    | 'presentation-script-review'
    | 'visual-review'
    | 'outcome-review'
  question: string
  reason: string
  blocking: boolean
  minSelections: 1
  maxSelections: 1 | 2 | 3
  options: Array<{
    id: string
    label: string
    description: string
    recommended?: boolean
  }>
  response?: {
    selectedOptionIds: string[]
    answeredBy: 'user' | 'approved-default'
    answeredAt: string
  }
}
```

调用结构化选择前必须做宿主能力预检。对 Codex 会话，需确认当前处于允许选择控件的计划模式且 `request_user_input` 可用；满足时将 `question`、`options[].label` 与 `options[].description` 原样映射为选项框。不满足时保存完整 `DecisionPrompt` 并进入 `decision-blocked`，只说明需要切换到可用模式，不能把选项复制成普通消息后假装完成同一门禁。恢复后继续使用相同决策 ID，避免两套答案。

`DecisionPrompt` 是外部 AI 编排协议，不是 Project V7 字段，也不是 Editor 1.x 已实现的 UI 或 AI 能力。

### 6.4 决策记录

每个获批选择、重要默认值和冲突处理都进入决策记录：

- 决策 ID 与时间；
- 问题和选项；
- 最终选择；
- 对教学设计、呈现或导出的影响；
- 是否允许后续实现阶段自行调整；
- 关联的权威来源。

实现阶段不得悄悄推翻决策记录。需要改变时退回相应审阅阶段。

## 7. 教学设计产物

教学设计回答“为什么教、教什么、如何证明学会”，不写 Project 节点、组件或运行时代码。

### 7.1 最小结构

```ts
interface TeachingDesign {
  title: string
  audience: {
    gradeOrLevel: string
    prerequisites: string[]
    usageContext: string
  }
  duration: string
  learningObjectives: string[]
  coreContent: string[]
  misconceptionsOrDifficulties: string[]
  evidenceOfLearning: string[]
  teachingStrategy: string
  sequence: Array<{
    id: string
    purpose: string
    learnerTask: string
    evidence: string
  }>
  assessmentAndFeedback: string[]
  constraints: string[]
  authoritativeSources: string[]
}
```

实际呈现可以是人类易读文档，不要求使用 TypeScript 或 JSON；结构字段必须能够被逐项检查。

### 7.2 设计原则

- 每个学习目标必须对应至少一个可观察证据；
- 每个教学阶段必须服务于目标、误概念纠正或迁移；
- 不因已有模板方便而加入无关测验、动画或总结页；
- 不把“看完了”“点过了”作为学习证据；
- 用户上传的已批准设计以保真实现为主，除非存在明确冲突；
- AI 生成设计时应给出实质不同的方向，而不是只改标题和视觉风格。

### 7.3 教学设计批准门禁

进入下一阶段前，人类至少确认：

- 学习目标和范围正确；
- 学习证据足以证明目标达成；
- 教学顺序和时长合理；
- 关键误概念、错误路径或安全要求没有遗漏；
- 所有必须保留的内容已经登记；
- 决策记录没有未解决的阻断项。

教学设计获批后赋予版本号并进入教学内容规格阶段。后续内容规格或呈现脚本若改变学习目标、内容边界或证据链，必须生成新版本并重新批准。

## 8. 教学内容规格

教学内容规格回答“本课到底准确教什么”，是教学设计与教学呈现脚本之间的强制交付边界。它不得只保存主题、活动名称或结果摘要；一个没有旧聊天、没有当前实现的新执行者必须能据此准确取得完整内容。

### 8.1 每个内容项的最小字段

```ts
interface ContentItem {
  id: string
  title: string
  teachingPurpose: string
  objectiveIds: string[]
  evidenceIds: string[]
  learnerVisiblePromptOrMaterial: string
  givensAndDefinitions: string[]
  expectedResponse: string
  completeReasoningOrExplanation: string
  acceptedAlternatives: string[]
  rejectedBoundaries: string[]
  misconceptionsAndFeedback: Array<{
    error: string
    cause: string
    firstResponse: string
    escalation: string
    repairedEvidence: string
  }>
  difficultyAndCognitiveDemand: string
  prerequisites: string[]
  revealPolicy: string
  estimatedMinutes: number
  authoritativeSources: string[]
  notationDiagramMediaRequirements: string[]
}
```

实际制品优先使用人类可审阅的 Markdown，并为目标、证据、内容项、错误和公式使用稳定 ID。不得为了结构化而把完整教学正文复制成第二套 JSON 真相。

### 8.2 内容规格要求

- 完整登记学生实际看见的题面、材料、已知条件、对象定义和任务要求；
- 给出标准答案或预期产出、完整推理、允许的替代路径和不接受边界；
- 解释干扰项和错误分支来源，不能只列“答错”；
- 用认知要求、先修关系和推理深度说明年级难度，不能只凭主题标签；
- 明确答案和关键结论在何时可见、何时不得提前出现；
- 对公式、符号、单位、图表、图示和媒体给出语义与专业排版要求；
- 给出整课容量表，包含独立思考、操作/讨论、反馈修复和教师检查点时间；页面数、点击数和动画时长不能代替教学容量；
- 权威事实必须关联来源；原创内容必须记录复核范围和剩余风险。

### 8.3 内容规格批准门禁

进入呈现脚本前，人类至少确认：

- 完整内容、答案与解释正确；
- 难度和内容量符合受众与时长；
- 典型错误、替代路径和反馈边界合理；
- 揭示顺序不会提前泄露应由学生形成的结论；
- 公式、图示、单位和学科表述要求完整；
- 没有需要后续呈现或实现阶段临时编写的核心内容。

教学内容规格获批后赋予版本号。后续脚本或实现若需改变题目、材料、答案、推理、难度、容量或揭示边界，必须返回本阶段生成新版本并重新批准。

## 9. 教学呈现脚本

教学呈现脚本是人类教学设计与技术实现之间的正式交付边界。它描述最终体验，但不要求人类理解 Project V7。

### 9.1 每个教学节拍的最小字段

```ts
interface PresentationBeat {
  id: string
  title: string
  teachingPurpose: string
  contentItemIds: string[]
  objectiveAndEvidenceRefs: string[]
  timeBudget: string
  initialView: string
  requiredVisibleBeforeAction: string[]
  teacherAction?: string
  learnerAction: string
  immediateResponse: string
  branches: Array<{
    condition: string
    response: string
    recoveryOrNext: string
  }>
  stableEndState: string
  transitionToNext: string
  revealPolicy: string
  teacherCheckpoint?: string
  visibleContent: string[]
  mediaAndSound: string[]
  keyMotion: string[]
  evidenceToCapture: string[]
  staticReviewFrame: string
}
```

### 9.2 编写要求

- 一幕可以包含多个稳定状态，但每个可达状态必须写清楚；
- 每幕必须引用已经批准的内容项、学习目标和学习证据，不得在脚本中临时编题；
- 学生第一次操作前，完成该操作所需的题面、条件、图示、定义和指令必须全部可见；
- 学生操作必须对应可见、及时且可理解的反馈；
- 成功、失败、未完成、重试和教师揭示不能只写成“按需处理”；
- 文字、媒体、声音和关键动效必须明确出现时机；
- 跨幕状态、解锁和返回路径必须写清楚；
- 每幕要有确定的静态审阅画面，供缩略图、PDF 和 PPTX 兼容检查；
- 不把底层节点类型或代码选择写进人类脚本；
- 当前模式允许有意使用幻灯片节奏，但不能无理由为每幕复制同一标题栏、卡片和导航壳。

### 9.3 呈现脚本审阅

人类审阅重点：

- 是否忠实实现已经批准的教学设计；
- 学生是否知道下一步做什么；
- 操作与反馈是否形成清楚的因果关系；
- 分支、失败和重试是否符合教学意图；
- 节奏是否过密、过碎或重复；
- 文案、声音和视觉是否存在不必要负担；
- 最终总结是否来自此前证据，而不是突然出现结论；
- 静态 PPTX/PDF 审阅画面是否仍有意义。

脚本批准后赋予版本号并进入 `presentation-script-review → visual-review` 或 `implementation-ready`。实现阶段若需改变学生看见的内容、操作、反馈或结束状态，必须退回脚本审阅。

## 10. 视觉方向、关键帧与核心样片

### 10.1 何时必须进行视觉审阅

出现以下任一情况时，不能从文字脚本直接批量实现：

- 用户强调美观、展示、竞赛、投资或旗舰质量；
- 使用新的视觉风格、复杂插画、真实装置、3D 或大量定制素材；
- 核心互动的构图和手势尚不确定；
- 实现成本高，错误路线会造成大量返工；
- PPTX 静态兼容与 HTML 动态效果可能明显分化；
- 没有可直接复用且已经接受的视觉方向。

### 10.2 最小视觉产物

- 视觉目标与避免事项；
- 与学科内容相关的视觉隐喻或场景语言；
- 色彩、字体、图形、影像和空间密度方向；
- UI 控件应出现的位置和可见程度；
- 动效原则：哪些运动表达因果，哪些只是装饰；
- 初始帧、核心互动帧和结果帧；
- 必需素材清单、来源和授权状态；
- 如有必要，一个可操作的核心互动样片。

视觉方向不等于整页模板。相同设计系统可以在不同教学节拍采用不同构图；PPTX 兼容要求稳定画面，不要求成品视觉模拟传统 PPT 模板。

### 10.3 人类门禁

人类确认：

- 主体、层级和操作位置正确；
- 视觉方向与受众、学科和使用场景匹配；
- 关键素材可获得且授权清楚；
- 核心互动值得继续实现；
- HTML 与静态兼容结果的预期差异可接受。

普通、低风险且已有接受方向的课件可以只提供视觉摘要并取得一次确认；不得用“低风险”跳过尚不明确的关键构图或素材决策。

## 11. 技术路径设计：默认内部完成

教学设计、教学内容规格、呈现脚本和必要视觉方向批准后，AI 才进入技术设计。

### 11.1 内部技术计划必须覆盖

- 每个教学节拍映射到哪些场景和稳定状态；
- 每项稳定视觉由哪些原生节点或组件承载；
- 哪些行为用声明式交互，哪些确需场景/全局运行时；
- 跨场景事件、`courseState`、重播和重开语义；
- 所有人工可见文字、素材和教师可编辑项的登记位置；
- 视觉素材、音频、视频和组件包的离线方案；
- 缩略图、PDF 和 PPTX 的静态审阅帧与后备；
- 生命周期、性能、安全和错误隔离；
- 真实操作、保存重开和导出的验收路径；
- 是否能复用已发布组件，或应保留为一次性实现。

建议内部使用映射表：

| 教学节拍/结果 | Scene/State | 稳定视觉 | 触发与反馈 | 技术承载 | 可编辑入口 | 静态结果 | 验收证据 |
| --- | --- | --- | --- | --- | --- | --- | --- |

### 11.2 不展示细节，不隐藏取舍

普通情况下，人类只看到“实现准备就绪”和简短的可感知结果摘要，不需要审核节点 ID、Schema 或渲染器。

以下情况必须暂停并返回人类：

- 需要付费工具、在线依赖、特殊许可证或人工 UI 操作；
- 无法取得关键素材或事实来源；
- 必须降低已经批准的视觉、互动、声音、分支或教学效果；
- PPTX/PDF 结果与已批准预期明显不同；
- 文件体积、低配设备或离线要求将受到明显影响；
- 技术限制要求改变教学呈现脚本；
- 需要对编辑器、Schema 或项目架构做超出任务范围的修改。

呈现的是产品影响和可选方案，而不是要求用户替 AI 设计底层实现。

### 11.3 实现入口

技术计划完成后，生成 `implementation-ready` 交接记录，然后完整执行 [Project V7 创作与接入规范](AI_COURSEWARE_AUTHORING.md)。不得跳过其文字可编辑性、状态、运行时、组件、生命周期、离线和导出要求。

## 12. `implementation-ready` 交接记录

实现阶段至少取得以下输入：

```ts
interface ImplementationHandoff {
  status: 'implementation-ready'
  projectTitle: string
  approvedTeachingDesignVersion: string
  approvedContentSpecVersion: string
  approvedPresentationScriptVersion: string
  approvedVisualDirectionVersion?: string
  approvedArtifacts: Array<{
    kind: 'teaching-design' | 'content-spec' | 'presentation-script' | 'visual-direction'
    path: string
    version: string
    sha256: string
  }>
  decisionLogIds: string[]
  authoritativeContent: string[]
  requiredAssets: string[]
  approvedAssumptions: string[]
  visibleEditabilityRequirements: string[]
  deliveryRequirements: Array<'h5lesson' | 'standalone-html' | 'web-package' | 'pdf' | 'pptx'>
  expectedStaticDifferences: string[]
  acceptanceEvidence: string[]
}
```

字段可以用人类易读方式表达，不要求真的保存为 TypeScript。批准必须绑定文件路径、版本和 SHA-256；内容变化后原批准和下游 readiness 自动失效。缺少获批教学设计、教学内容规格或呈现脚本时，不得伪造版本号后继续。

## 13. 实现、变更控制与返工

### 13.1 实现原则

- 以批准教学内容规格和呈现脚本为结果真相，以 Project V7 为工程真相；
- 先完成代表性高风险场景或核心互动，再扩展重复部分；
- 视觉效果弱于批准关键帧时停止下游扩展并修正路线；
- 技术失败不能擅自删除教学状态、互动、声音或分支；
- 可复用候选不应在首次实现时强行抽象为通用框架；
- 实现过程只汇报用户可验证的阶段结果和重大风险。

### 13.2 变更分级

| 变化 | 处理方式 |
| --- | --- |
| 节点 ID、代码组织、等价实现替换 | AI 内部处理 |
| 不改变脚本的细节修复和性能优化 | AI 内部处理并验证 |
| 文案小改但不改变教学含义 | 记录后实现；权威文案除外 |
| 改变操作、反馈、分支、视觉主体或节奏 | 返回呈现脚本/视觉审阅 |
| 改变题面、材料、答案、推理、难度、容量或揭示边界 | 返回教学内容规格审阅 |
| 改变学习目标、证据链或内容边界 | 返回教学设计审阅 |
| 引入付费、授权、联网或重大终端差异 | 暂停并请求批准 |

## 14. 结果验收与接受

### 14.1 管线证据

- Schema、工程检查和素材引用；
- 保存、关闭、重开和恢复；
- 场景、状态、声明式交互、运行时和组件生命周期；
- 单 HTML 与网页包离线运行；
- PDF/PPTX 静态化和差异报告；
- 类型检查、测试和构建。

### 14.2 结果证据

- 呈现脚本中每个核心节拍的稳定状态截图；
- 核心互动的真实操作录屏或等价可复查证据；
- 成功、失败、重试、分支和结束路径；
- 文案、素材和公开参数的实际编辑证据；
- 统一画布试运行和整课 HTML 播放；
- PDF/PPTX 的真实打开和静态结果；
- 与批准教学设计、脚本和关键帧的差异清单；
- 未实现项、终端差异和剩余风险。

### 14.3 状态词

统一使用：

- `unusable`
- `placeholder`
- `engineering candidate`
- `art candidate`
- `accepted`

测试通过最多证明 `engineering candidate`；视觉和互动证据达到预期但尚未取得最终批准时可以是 `art candidate`；只有批准人明确接受后才能标记 `accepted`。

### 14.4 人类结果审阅

人类审阅不需要检查技术实现，只需确认：

- 是否忠实实现教学设计、教学内容规格和呈现脚本；
- 学生能否理解操作并从反馈获得正确证据；
- 视觉、节奏、声音和关键动效是否达到预期；
- HTML 与 PPTX/PDF 差异是否可接受；
- 是否需要修改、接受或终止。

任何修改决定进入新修订，重新执行受影响范围的设计或实现门禁。不得在用户要求修改时仍保留 `accepted`。

## 15. 接受成品后的复用沉淀

### 15.1 四级成熟度

```text
accepted 成品
  → 参考案例
  → 候选模式
  → 已批准模板
  → 已发布组件
```

并非每个案例都会到达最后两级。

### 15.2 参考案例

每个 `accepted` 成品可以登记案例卡：

- 学科、年级、主题和课程标准；
- 学习目标、误概念和学习证据；
- 使用场景和时长；
- 教学呈现结构；
- 关键互动和视觉方向；
- 使用的素材、组件和许可证；
- HTML、PDF、PPTX 结果差异；
- 验收证据、接受者和版本；
- 哪些内容高度专属，不适合复用。

案例卡用于检索和参考，不自动成为模板。

### 15.3 候选模式

多个接受案例出现相似结构后，提取：

- 不变的教学机制；
- 可替换的内容槽位；
- 适用和不适用条件；
- 对学习证据的贡献；
- 视觉上必须保持灵活的部分；
- 需要的技术能力和静态后备。

相似性优先比较教学目标、学习行为、反馈和证据链，不按主题关键词或页面外观直接判定。

### 15.4 模板晋升

模板必须经过至少两个独立内容样例验证其不变项和可变项；具体数量可按风险提高。模板应描述教学节拍、信息结构、互动模式和插槽，而不是复制整页视觉壳。

模板必须包含：

- 适用目标和前提；
- 必需输入和可变项；
- 教学节拍与分支；
- 允许改变的视觉范围；
- 禁止套用的情况；
- 验收清单；
- 来源案例和版本。

### 15.5 组件晋升

只有在行为重复、参数边界稳定、独立维护有价值时才组件化。正式组件必须补齐：

- 稳定 ID、版本和作用域；
- 明确 Props、全部可见文案和公开参数；
- DOM/Phaser/hybrid 能力声明；
- 创建、更新、resize、显隐、暂停、恢复和销毁；
- 离线素材、缩略图和静态捕获；
- 编辑、播放、重播、切页和压力测试；
- 来源、许可证、维护者和弃用策略。

一次性高质量效果可以永久保留为案例实现，不因“沉淀”要求被迫组件化。

### 15.6 不追溯改写接受成品

模板或组件后续升级不得静默改写已经接受的历史工程。历史工程继续引用其版本；新课件可以选择新版，旧工程升级必须显式执行并重新验收。

## 16. 未来学科上下文的挂载边界

本节定义未来可组合上下文的责任，不定义未实现的产品 UI 或存储系统。

### 16.1 学科知识资料

负责事实与约束：

- 核心概念、定义、公式和术语；
- 课程标准、年级范围和先修关系；
- 常见误概念、典型错误和评价证据；
- 实验安全、单位、符号和学科规范；
- 权威来源、版本、地区和复核日期。

知识资料不能直接规定整页设计，也不能替代本次教学设计批准。

### 16.2 学科创作说明

负责学科特有的教学与呈现建议：

- 概念如何表征和逐步建立；
- 适合的实验、图表、语言、例题和互动；
- 反馈如何避免强化误概念；
- 不同年级的认知负担和表达边界；
- 学科特有的质量与事实验收。

它在教学设计、教学内容规格和呈现脚本阶段生效，不得覆盖平台硬约束和用户批准内容。

### 16.3 素材记录

素材库条目至少应包含：

- 稳定 ID、名称、类型和版本；
- 学科、年级、概念和使用场景标签；
- 文件格式、尺寸、比例和透明背景信息；
- 来源、作者、许可证、署名和商用/修改/再分发条件；
- 替代文本和敏感内容说明；
- 推荐用法、禁止用法和静态导出表现。

素材在教学和视觉需求确定后检索，不能因“库里已有”而改变学习目标。

### 16.4 模板与组件目录

模板目录记录教学适用性、插槽和来源案例；组件目录记录技术能力、Props、作用域、性能、兼容导出和版本。两者必须分开检索和治理。

呈现脚本批准后可以检索相似模板；技术设计阶段可以检索组件。若复用会改变用户已经批准的体验，必须返回人类确认。

### 16.5 来源与复现

未来上下文系统应能够在构建报告中记录本次实际使用的知识、学科说明、素材、模板和组件版本。记录用于复现和审计，不要求把完整知识库塞进 `.h5lesson` 或发布 HTML。

## 17. 快速路径与引导路径

### 17.1 引导路径

适用于只有主题、部分教案、高风险内容、新视觉方向或复杂互动的任务。完整执行上下文诊断、结构化选择、教学设计、教学内容规格、呈现脚本、视觉审阅、技术实现和结果验收。

### 17.2 快速路径

适用于：

- 已提供并批准的完整教学设计；
- 呈现结构简单且无高影响不确定项；
- 使用已经接受、适用范围明确的方向；
- 不涉及付费、授权、重大终端差异或架构改造。

快速路径仍必须：

1. 给出输入摘要与假设；
2. 补齐并确认可供冷启动实现的教学内容规格；
3. 生成并确认教学呈现脚本；
4. 完成内部技术计划；
5. 提供真实结果证据；
6. 取得接受状态。

快速不等于跳过设计，而是减少没有决策价值的往返。

### 17.3 已接受课件的小修路径

如果修改不改变学习目标、呈现脚本、关键视觉或交付语义，可以直接进入技术变更和受影响范围回归。以下修改不能按小修处理：

- 新增或删除教学阶段；
- 改变学生操作、反馈或分支；
- 替换关键视觉方向或主体素材；
- 改变 PPTX/PDF 静态结果；
- 修改权威内容或学习证据。

## 18. 对话与交付界面

AI 在不同阶段只展示用户需要判断的内容：

| 阶段 | 默认展示 | 默认不展示 |
| --- | --- | --- |
| 输入诊断 | 材料摘要、缺失项、冲突 | Project 字段 |
| 选择 | 1–3 个高影响问题和后果 | 底层技术选型 |
| 教学设计 | 目标、证据、顺序、边界 | 节点/组件计划 |
| 教学内容规格 | 完整内容、答案、推理、难度、容量和揭示规则 | Project 字段与代码 |
| 呈现脚本 | 画面、操作、反馈、分支、节奏 | Schema 和代码 |
| 视觉审阅 | 关键帧、样片、素材和差异 | 生命周期细节 |
| 实现 | 简短进度、重大风险 | 普通代码组织 |
| 结果审阅 | HTML、截图、录屏、导出和风险 | 无关测试日志 |
| 复用审阅 | 案例卡和候选模式 | 自动晋升决定 |

每次请求确认都必须说明“确认什么、确认后会进入哪一步、以后什么变化会要求重新确认”。

## 19. 禁止的编排行为

以下均视为流程失败：

- 从不完整主题直接生成最终 `.h5lesson`，再让用户从成品中发现需求问题；
- 只保存教学目标和活动名称，不落盘完整教学内容规格便进入呈现或实现；
- 为了显得严谨而询问所有低影响细节；
- 让普通用户选择 DOM、Phaser、组件 API 或 Project Schema；
- 未经批准擅自改变用户教学设计；
- 在呈现脚本前先套模板或选择现成组件；
- 因素材库缺少内容而删除教学环节；
- 把学科知识建议冒充用户指定的权威结论；
- 未经视觉审阅就批量实现高成本、高审美场景；
- 技术实现失败后静默降低互动、声音、分支或视觉；
- 没有真实证据便把结果标为 `accepted`；
- 第一个成功案例就自动抽象成通用模板或组件；
- 把未来规划能力写入当前 Project V7 成品或用户功能说明。

## 20. 最终原则

通用创作编排层遵守以下原则：

1. 先确认教学设计，再冻结教学内容规格，再确认教学呈现，最后决定技术实现；
2. 人类决定教学目标、关键体验和可感知取舍，AI 承担普通技术细节；
3. 只询问会实质改变结果的问题，其他事项使用可追踪默认值；
4. 视觉方向属于设计，不属于可以完全隐藏的技术实现；
5. 只有被人类接受的成品才能进入复用沉淀；
6. 学科知识、学科创作说明、素材、模板和组件各自独立治理；
7. 已有模板和组件服务教学设计，不能反向统治教学设计；
8. 当前生成协议只描述真实存在的 PPT 兼容 Project V7 能力；
9. 管线通过不是成品接受；
10. 编排层最终交付的是一份获批、可实现、可验收的体验合同。
