## 0. 结论摘要

不需要停下来做架构级修复。功能与稳定性均为绿，报告的三个问题里一个是误判，两个属于已登记的收尾项。

但有一项不会随开发自愈，需要立为独立专项：**编辑器缺少"这门课是什么形态"的概念**，导致纯讲义课也要背着跨类型导航，混合课又从未被专门设计过。这是"几个模式混在一起、杂乱无章"的根因，不是视觉细节问题。

| 报告的问题 | 核查结论 |
| --- | --- |
| 画布级编辑不可用 | **误判**。实机 19 项全通。真实诱因是简洁模式隐藏坐标 + Flow 无画布内文字编辑 |
| 很多功能没开放 | **成立**，但多数是模式门控（默认露 3 页签 / 专业露 6 页签），少数是迁移期硬门控 |
| UI/UX 完全不对 | **成立**，且是信息架构问题。视觉一致性另有量化缺口，属另一件事 |

**产生"不可用"印象的两个真实原因：**

1. **默认简洁模式隐藏 X/Y。** 实测简洁模式几何字段读取为 `{}`，专业模式才有 `{x,y,w,h,rot}`。见 [`PropertiesTab.tsx:753`](src/renderer/ui/PropertiesTab.tsx:753) 起三处 `editorMode === 'professional'` 门控。看不到坐标，容易以为拖动没生效。
2. **Flow 无画布内文字编辑。** [`FlowWorkspace.tsx`](src/renderer/ui/FlowWorkspace.tsx) 中 `onDoubleClick`/`contentEditable` 命中数为 **0**；Slide 的 `EditorScene.ts` 有 2 个双击派发器。Flow 只有 7 个结构工具条按钮，正文只能走属性栏。

另有一层设计使然的能力门控，[`workspaceSlideAuthoring.ts:160`](src/renderer/ui/workspaceSlideAuthoring.ts:160)：

```ts
export function workspaceAuthoringActionAllowed(injected, action): boolean {
  if (!injected) return true
  return (
    (action === 'text-edit' && injected.onTextEditCommit !== undefined) ||
    action === 'runtime-edit' || action === 'component-edit'
  )
}
```

V9 后端下 `formula-edit`、`drop`、`animation-preview`、`ai-reference`、`run-current-location` 一律拒绝。这是 V8→V9 迁移期的显式取舍。

### 1.4 信息架构：真正的问题

[`ScenePanel.tsx:611`](src/renderer/ui/ScenePanel.tsx:611) 的 Flow 分支，左栏垂直堆叠了三层性质不同的东西：

```
<aside class="scene-panel">
  {courseLocationNav}     ← 跨表面导航：幻灯片/讲义/空间 混排一个平铺列表
  <h2>Flow 讲义</h2>       ← 当前表面类型标题
  {surfaceTitle}          ← 当前表面名
  <FlowOutlinePanel/>     ← 正文大纲（讲义段落结构）
</aside>
```

`courseLocationNav` 把全课程位置摊成一个列表，每项贴 `data-kind` 标签（`幻灯片`/`讲义`/`空间`，见 [`ScenePanel.tsx:105`](src/renderer/ui/ScenePanel.tsx:105)）。也就是说**纯 Flow 工程里，左栏顶部仍挂着跨表面导航，下面才是正文大纲**——一个是课程级跳转，一个是文档级结构，同处一个 `aside`，仅靠 `panel-header` 分隔。Spatial 分支（[`:645`](src/renderer/ui/ScenePanel.tsx:645)）同形，只把大纲换成镜头列表。

**根因是没有工程形态概念。** [`App.tsx:489`](src/renderer/App.tsx:489)：

```ts
const activeCourseEditorRoute = v9SlideVerticalSlice === null ? 'legacy'
  : v9ActiveSlideContext !== null ? 'slide'
  : v9FlowEditorView !== null ? 'flow'
  : v9SpatialEditorView !== null ? 'spatial' : 'unavailable'
```

这是**逐位置切换**，不是**模式**。壳层只知道"光标停在哪"，不知道"这门课整体是什么形态"。后果：纯讲义工程也要背跨表面导航，混合工程则毫无专门编排——只是三套分支的分时复用。

工程文件格式（[`courseProjectSchema.ts:1123`](src/shared/courseProjectSchema.ts:1123)）中**没有任何形态字段**：

```
schemaVersion, id, revision, title, createdAt, updatedAt, assets,
componentPackages, designTokens, media, playback, courseState,
navigationGuards, locations, startLocationId, globalLayerItems,
globalInteractions, surfaces, mixedPrintPlan?
```

## 2. 四模式设计

### 2.1 原则

1. **工程形态是一等概念**，决定壳层布局；当前位置只决定内容区。
2. **纯模式左栏只做一件事。** 三个纯模式基本是减法，混合模式是唯一需要真设计的。
3. **混合模式：壳不变，只有中间换。** 现在换一种内容左栏整个换样，是杂乱感的直接来源。
4. 形态由建档时显式选择，可改；不随内容自动变脸。

**可逆性已核实。** `locations` 是平铺列表（`min(1).max(100_000)`），任何类型可共存、无排他：

## 3. 幻灯片三层模型与锁定机制

### 3.1 收紧后的定义

- **幻灯片全局层**（原"全局层"，改名）：属于这一叠幻灯片，不跨类型。定义**有哪些**常驻元素（页码、校徽、控制器）。它是一个**统一修改入口，不是元素的归属地**。
- **每一页**：管这一页**怎么显示、要不要显示**。
- **"增"走该页自己的内容**：只属于一页的元素本质就是该页内容，不必挂在全局层。这样避免两个概念抢同一件事。
- **教师控制器组件化**：视作默认载入的普通节点，走同一套摆放/锁定/单页调整规则，不再是特殊功能。

**单页覆盖能力已存在。** [`layerItemOverrideSchema:436`](src/shared/courseProjectSchema.ts:436) 支持逐状态覆盖：

```
label, frame(mode/x/y/width/height), order, visible, locked,
rotation, opacity, hitPolicy, playbackInitialVisibility,
nativeData, componentProps
```

覆盖记在 `slidePresentationStateSchema.layerItemOverrides` 上——改"基础状态"即改这一页常态，与"母版类的东西放在各场景基础状态中"是同一件事。

### 3.2 锁定：现状与缺口

**锁定不是废的，但漏了两个关口——恰是它要承重的两个。**

已生效：

| 位置 | 行为 |
| --- | --- |
| [`NodesTab.tsx:225`](src/renderer/ui/NodesTab.tsx:225) | 图层页锁按钮 |
| [`EditorScene.ts:160,279`](src/renderer/phaser/EditorScene.ts:160) | 锁定后不可拖动 |
| [`EditorScene.ts:320`](src/renderer/phaser/EditorScene.ts:320) | 锁定后不可选中、双击进不去文字编辑 |
| [`slideEditorCommands.ts:135`](src/renderer/course/slideEditorCommands.ts:135) | 手势命令层 `throw new Error('当前元素已锁定')` |
| [`spatialEditorCommands.ts:269`](src/renderer/course/spatialEditorCommands.ts:269) | 同上（画布侧） |
| [`v9SlideVerticalSlice.ts:2505`](src/renderer/course/v9SlideVerticalSlice.ts:2505) | 复制出的副本自动解锁 |

**缺口（`src/renderer/course/*.ts` 全量 grep `locked`，仅上述两处 throw 守卫）：**

1. **删除路径未见锁定守卫** —— 锁定只挡"改"，没挡"删"。
2. **属性栏路径未见锁定守卫** —— 画布上拖不动，但去属性栏直接改数值仍生效。

这两处必须补齐，否则"锁定后无法删改"只兑现一半。

### 3.3 已定的锁定语义

| 条目 | 决定 |
| --- | --- |
| 选中 | **不拦**。可选中、可看属性、不可编辑，选中时直接给解锁按钮 |
| 继承语义 | **冻结**。锁定时是什么样就一直是什么样，全局层后续改动一概不跟 |
| 全局层删除时 | 锁定页面**自动保留、不弹提示**。因为全局层只是统一修改入口，其节点本来就同时存在于各页面；锁定已声明不跟随 |
| 删除后的可见性 | 那些页面的图层里显示「已锁定 · 不再跟随全局」，平时可见，不打断操作 |
| AI 改动 | 与人走同一道门。锁定后 AI 亦不可改，必须先解锁 |

**锁定与隐藏是两件事，不可混用。** 锁定 = 我说了算；隐藏 = 这页不显示。一个元素可以"锁定且显示"、"锁定且隐藏"、"没锁但隐藏"。不要把"这页不要它"做成"锁定它"。

### 3.4 锁定元素在属性栏

```
┌─ 属性 ──────────────────┐
│ 校徽            🔒 已锁定│
│                          │
│  ┌────────────────────┐  │
│  │      解锁后编辑     │  │
│  └────────────────────┘  │
│                          │
│  X    120   Y    40      │  ← 灰显只读
│  宽    80   高    80      │
│                          │
│  🔒 不再跟随幻灯片全局层  │
└──────────────────────────┘
```

### 3.5 建议移除的重复机制

"这一页不显示某全局元素"现有**两条路**：

1. [`locationVisibilitySchema:406`](src/shared/courseProjectSchema.ts:406) —— 全局层自己维护 `mode: 'all'|'include'|'exclude'` + `locationIds` 名单
2. `layerItemOverride.visible` —— 页面自己声明

两个机制干同一件事，是"改了没反应"的经典来源。既然形态已定为"每页分别管理"，建议：**页面层面的显示/隐藏作为唯一入口，全局层不再维护跨页名单。** 这同时消掉"混合课里名单要跨三种坐标系"的问题。

> 这是本次唯一影响既有工程行为的改动，需在迁移时明确处理存量 `include`/`exclude` 数据。

## 4. 全局层改动的应用机制

### 4.1 问题

锁定解决了"已声明我说了算"的页面，但留下一类：**改过但没锁定的页面**。全局层若直接生效会覆盖它们的改动；每次改都提示则过于频繁。

### 4.2 已定方案：先编辑、后应用

全局层内改动不立即生效，攒起来一次应用。

```
┌─ 应用全局层改动 ─────────────────────────┐
│                                          │
│  本次改动：校徽位置、页码字号             │
│                                          │
│  ✓ 12 页 跟随全局，将一起更新             │
│  🔒 3 页 已锁定，保持不变                 │
│                                          │
│  ⚠ 2 页 单独改过但没锁定：                │
│      第 5 页 · 第 9 页                   │
│    ○ 一起更新（覆盖这两页的改动）        │
│    ● 保持不变（自动为这两页上锁）        │
│                                          │
│                    取消    应用          │
└──────────────────────────────────────────┘
```

两个设计点：

- **只有第三类需要决定。** 前两类只是告知。
- **选"保持不变"顺手上锁。** 这个决定只做一次，下次改全局层它们已在"已锁定"栏。这补上"防止忘记上锁"。

无第三类页面时不弹窗，直接生效——绝大多数情况无感。

### 4.3 全局层视图

```
├──────────────┬─────────────────────────────────┬─────────────────┤
│ 幻灯片    ＋ │                                 │ 元素 图层 属性  │
│              │     ┌─────────────────────┐     │                 │
│ ┌──────────┐ │     │ 校徽            页码│     │ 幻灯片全局层    │
│ │▣ 1  封面 │ │     │                     │     │                 │
│ └──────────┘ │     │  （当前页内容淡显）  │     │ 🔒 校徽         │
│      ⋮       │     │                     │     │ 👁 页码         │
│              │     │        ▮控制器      │     │ 👁 控制器       │
│ ┈┈┈┈┈┈┈┈┈┈┈ │     └─────────────────────┘     │                 │
│ ┏━━━━━━━━━━┓ │                                 │                 │
│ ┃▤ 幻灯片  ┃ │   有 2 项改动尚未应用           │                 │
│ ┃  全局层  ┃ │   ┌───────────────────────┐     │                 │
│ ┗━━━━━━━━━━┛ │   │  应用到全部幻灯片      │     │                 │
│              │   └───────────────────────┘     │                 │
```

编辑器**没有任何"改完再应用"的先例**（全量 grep `应用更改`/`pendingEdit`/`draftValue`/`stagedChange` 均无命中）。所有编辑都是即时生效、即时进历史。这是本次唯一的新交互范式，落地前值得单独确认。

## 5. 开发建议

### 5.1 不停工

构建绿、零运行时错误、画布编辑实测全通、M5/M6 的 P1/P2 已 integrated。未触及根计划 §7 停工条件（新依赖、不可逆破坏、权限阻塞、契约冲突）。

### 5.2 三个专项，不要混做

| 专项 | 内容 | 理由 |
| --- | --- | --- |
| **A. 四模式信息架构** | 形态概念 + 四套左栏 + 混合编排 + 形态切换 | 本文档主体。不会随开发自愈 |
| **B. 锁定机制补全** | 补删除/属性栏两道守卫 + 不拦选中 + 冻结语义 + 全局层应用机制 | A 的承重墙，须先立起来 |
| **C. 视觉系统收敛** | 建字阶/圆角/间距令牌 → lint 级约束禁止新增裸色值裸 px → 存量分批替换 | 与 A/B 无关；需独立门禁，混做会被功能项挤掉 |

### 5.3 推进顺序

1. **B 先行**（锁定守卫补齐）——A 的全局层设计依赖锁定可信。
2. **形态概念落地**：新增形态字段、存量工程默认推导、混合↔纯的切换与灰显条件。
3. **三个纯模式左栏**（减法为主）。
4. **混合编排**（唯一需真设计的）。
5. **Flow 画布内文字编辑**——纯讲义模式的前提，否则模式再干净也不好用。
6. **C 独立排期**。

### 5.4 顺带处理的既有缺口

| 项 | 处理 |
| --- | --- |
| 简洁模式隐藏 X/Y 导致误判"画布编辑不可用" | 简洁模式也显示坐标（只读亦可），或画布拖动后状态栏回显坐标变化。低成本高收益 |
| DOCX 禁用原因只在 `title` | 菜单项内联可见原因 |
| 术语泄漏 20 处 | 随 A 一并清理（对应 P3 第 12 项） |
| 1366×768 画布仅占 32.4% | 纯模式左栏收窄 + 左栏可收起；建议给 1366×768 定量目标（≥45%） |

### 5.5 约束与风险

**保壳门禁会拦。** [`verify-editor-preservation.ts:87`](scripts/verify-editor-preservation.ts:87) 将 `App.tsx`、`TopToolbar.tsx`、`ScenePanel.tsx`、`Workspace.tsx`、`RightSidebar.tsx`、`globals.css` 等列入受保护路径，并绑定 token 断言（`scene-panel`、`right-sidebar`、`data-testid="top-toolbar"`）与 `goldenViewports` 像素基线。

改左栏信息架构必然触发。两条合法路径：

1. 在门禁中为新布局**显式登记新基线**；
2. 把四模式壳层做成 `scene-panel` **之下的编排层**，保住既有 token 与结构骨架。

选错的后果：要么门禁红，要么改不彻底又留一层壳。**四套界面每套都要重新过一遍该检查**，这影响进度预期。

**工程文件格式要 bump。** 新增形态字段意味着：老工程无该字段需默认推导；存新格式的工程在旧构建上可能打不开。这与 P3 第 14 项（`schemaVersion` 未随 strict 新字段 bump）应合并处理。

**移除 `locationVisibility` 是唯一影响存量数据的改动**，需明确迁移策略。
