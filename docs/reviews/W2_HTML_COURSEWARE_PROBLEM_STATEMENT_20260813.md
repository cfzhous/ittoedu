- 兼容形态：PDF、PPTX，仅要求静态可读、内容完整和差异诚实，不以对象级还原作为当前主目标
- 涉及课例：高中数学“二次函数＋判别式”、高中语文《赤壁赋》证据路径

## 1. 希望其他 AI 研判什么

1. 课程设计合同或精确内容；

3. V8 Builder 的载体选择与实现；

两个 W2 课例均通过了现有结构校验、Project 校验、编辑保存重开、HTML/网页包和证据校验，manifest 标记为：

## 3. 用户观察到的三个主要问题

### 3.1 教师全局控制缺失

用户在 HTML 成品中看不到教师全局控制器。数学工程中即使存在控制器节点，仍完全不显示；因而无法稳定执行上一幕、下一幕、重播、重置、揭示或带未完成继续。

这不是上游教学脚本遗漏。两份脚本都明确要求教师控制场景推进、揭示、重置和未完成时接管。

### 3.2 HTML 工程过度 Runtime 化

大量稳定题面、正文、标签、反馈和布局被放进全屏场景 Runtime。结果虽然 HTML 可以显示，但教师在编辑器中难以把这些内容当作独立画布对象定位、选择和调整；编辑入口主要退化为 Runtime 属性文本。

PDF/PPTX 快照只是这个载体选择的旁证，不是当前主矛盾。核心问题是 HTML 主产品的教师创作与修改体验，以及全屏 Runtime 对全局控制层的影响。

### 3.3 题量、判题和阻断流程失真

- 数学课例在 15 分钟内包含大量输入、判断、改写和迁移作答；实际实现约有 21 个响应槽，获批脚本计划的响应单元更多。
- 数学开放字段由手写正则和关键词组合判定。等价数学表达、全角标点、自然语言变体可能被拒绝；部分关键词拼接又可能被误判为正确。
- 语文脚本要求真实圈画、片段对应、引用和解释，但成品前三幕主要通过“错误 / 完成”一类分支按钮直接切换状态，并未真正收集脚本规定的学生证据。
- 语文最后的 40 字结论使用关键词正则判定，既可能拒绝合理同义表达，也可能接受语义薄弱的关键词拼接。
- 机器不接受答案时，课内下一步入口被隐藏；教师控制器又不可见，因此实际形成死锁。

## 4. 已确认的代码与工程事实

### 4.1 默认控制器本来存在

[createProject.ts](../../src/renderer/project/createProject.ts) 中：

- `includeDefaultController` 默认值为 `true`；
- 默认控制器进入 `globalLayer`；
- 默认 `playback.controls` 为 `canvas`。

两个课例却分别出现：

| 课例 | `playback.controls` | `globalLayer` | 场景构成 |
| --- | --- | --- | --- |
| 数学 | `none` | 1 个 `teacher-controller` | 4 幕均有 scene Runtime；每幕另有 1 个原生 FormulaNode |
| 语文 | `none` | 空 | 4 幕均为 Runtime；原生场景节点为 0 |

数学 Builder 先以 `includeDefaultController: false` 建工程，再手工加入控制器，却没有同步把 `playback.controls` 改回 `canvas`。

[renderTeacherController.ts](../../src/player/renderTeacherController.ts) 会在 `canvasControlsEnabled` 为假时主动隐藏控制器。因此，“工程里有控制器但不显示”首先是工程配置自相矛盾。

此外，[editorStore.ts](../../src/renderer/store/editorStore.ts) 的 `ensureTeacherController()` 在控制器不存在时会同时修复 `playback.controls`，但发现节点已存在时只定位节点，不修复 controls。已有坏状态因此会持续存在。

### 4.2 Player 存在跨渲染平面的层级风险

[PlayerApp.ts](../../src/player/PlayerApp.ts) 当前层级为：

```text
global DOM underlay: z=0
scene DOM underlay:  z=1
Phaser canvas host:  z=2
scene DOM overlay:   z=3
global DOM overlay:  z=4
```

原生 `TeacherControllerNode` 位于 Phaser Canvas 内。即使其 Phaser depth 属于 global overlay，也无法越过整个 Canvas 外部、`z=3` 的全屏 scene Runtime DOM overlay。

因此存在第二个独立风险：即使修正 `playback.controls`，全屏场景 Runtime 仍可能覆盖原生全局控制器。需要判断这是 Player 合成模型缺陷，还是应改用独立的全局 DOM 控制平面。

### 4.3 Runtime 使用比例

Authoring Inventory 的摘要：

| 课例 | 场景所有权 | 登记实体 | 原生绑定 | Runtime 绑定 | `property-only` |
| --- | --- | ---: | ---: | ---: | ---: |
| 数学 | 4 幕 `hybrid-owned` | 15 | 4 | 11 | 7 |
| 语文 | 4 幕 `runtime-owned` | 86 | 0 | 86 | 32 |

语文所谓 `visible` Runtime 文本仍不是独立原生画布节点。Runtime Authoring 注册大量文字时，多数共享整幕或大区域 bounds；这能提供属性入口，但不能等同于逐对象画布编辑。

数学名义上是 hybrid，实际每幕只有一个原生公式，其余题面、输入、反馈、图象和布局主要由 Runtime 拥有。

### 4.4 现有判题实现没有通用等价层

当前核心仓库未发现共享的答案归一化、数学表达等价或开放回答评估器。两个课例各自在 Runtime 中手写逻辑。

数学典型行为包括：

- 检查 `f(x)=0` 的固定字符串形式；
- 用“是否包含 0 和 2”判断根；
- 用固定半角括号、逗号模式判断坐标；
- 用少量关键词判断解释是否成立。

这既会产生假阴性，也会产生假阳性。对于开放数学解释和语文证据表达，单纯扩大正则列表不是可靠方向。

## 5. 上游合同和脚本是否也有问题

结论不是“只修执行侧”。上游有可保留部分，也有必须重开部分。

### 5.1 可以保留

- 数学“图象—方程—判别式—不同交点”的目标与例题关系正确；
- 语文“景中有乐—有限之悲—变 / 不变双重视角—共适清风明月”的证据链完整；
- 两边都定义了典型错误、分层反馈、可接受替代和拒绝边界；
- 两份脚本都明确了教师控制、重试、揭示、恢复以及未完成继续；
- 当前未发现需要推倒重写的核心学科事实问题。

### 5.2 必须重开

#### A. 15 分钟容量

数学脚本计划至少包括：

- 图—式桥接四项；
- 三行预测的 9 个单元；
- `FORM-002` 六空和解释；
- 三项判断、两条改写；
- 参数、交点、理由三项迁移。

语文脚本计划包括：三段长文阅读、三个位置、三处圈画、两句因果解释、成对证据反驳和 40 字结论。

合同目前以“各阶段分配几分钟”证明容量，却没有对必答单元、平均输入时间、典型错误重试和教师讨论时间建立可检验预算。形式上总和为 15 分钟，不代表真实课堂可完成。

#### B. 学习证据与数字字段混淆

“需要观察的学习证据”不应自动变成“每一项都必须由学生在页面输入”。应区分：

- 页面必须采集的结构化答案；
- 教师口头抽查或课堂观察；
- 学生纸笔完成、页面只负责揭示和对照；
- 只用于教师讨论、不应成为导航硬门禁的开放表达。

#### C. 判定权威没有冻结

精确内容虽然列出替代答案，但合同没有明确区分：

- 有限选项自动判定；
- 经规范化即可判定的短答案；
- 需要数学等价处理的表达；
- 必须由教师、自评或同伴评价的开放答案。

Builder 因而把“有成功标准”误解为“应由 Runtime 自动硬判”。

#### D. 对产品能力作了未经确认的假设

脚本多处要求教师查看全班预测分布、错误人数或常见缺口，但没有确认多人数据来源、课堂端架构或隐私边界。这些能力没有在当前单机 Project V8 中实现，也不应由 Builder临时猜造。

#### E. HTML 编辑结果没有成为明确合同

不需要在教学脚本里指定 native 或 Runtime，但应冻结结果级要求，例如：

- 哪些稳定题面、正文、反馈和教师提示必须方便在编辑器中修改；
- 哪些复杂动态图象或交互允许由 Runtime 整体拥有；
- 编辑后保存、重开和 HTML 输出必须保持一致。

## 6. 当前校验为什么没有拦住

现有门禁主要证明：

- 文件和容器是真实产物；
- Project Schema 与引用有效；
- 预设初始、反馈、稳定帧存在；
- 一条自动化黄金路径可以到达稳定状态；
- 某些 Runtime 文本可通过属性入口修改、保存和重开；
- HTML、网页包、PDF、PPTX、截图和录屏存在且哈希闭合。

但没有证明：

- 每一幕中教师控制器真实可见、无遮挡且按钮可点击；
- 错误答案后可以重试、揭示或由教师带未完成继续；
- 正确但不同表述的答案能通过，错误关键词拼接不能通过；
- 脚本要求的圈画、拖放、填写确实由学生完成，而非测试直接切状态；
- Authoring Inventory 的 `visible` 真的是逐对象可编辑，而不是一个 Runtime 大区域入口；
- 15 分钟容量在真实交互节奏下成立；
- `engineering candidate` 已达到教师可用的 HTML 产品候选水平。

## 7. 建议作为研判基准的 HTML 主门禁

以下只是待评审候选，不是已经决定的方案。

1. **教师控制可达性**：每幕真实 Player 截图和交互测试中，控制器必须可见、位于最高操作层，并实际执行上一幕、下一幕、重播和重置。
2. **教师逃生路径**：任意错误或空白状态下，教师都能揭示、跳过或带未完成继续；不能依赖学生先答对。
3. **脚本动作真实性**：脚本写圈画、拖放、输入或参数操作，E2E 必须通过对应真实控件产生证据，禁止直接设置 Presentation State 冒充。
4. **答案容错矩阵**：至少覆盖标准答案、等价正确答案、全半角和空白变体、典型近错、关键词拼接假阳性。
5. **开放回答不硬锁**：没有可靠语义判定能力时，开放回答只能自检、提示或教师判定，不能成为唯一导航条件。
6. **HTML 编辑闭环**：按载体类型修改关键内容，保存、关闭、重开，并验证 Player 和 HTML 都更新；`visible` 必须有真实可定位区域。
7. **载体降级显式化**：若稳定内容从预期的画布可编辑降为 Runtime 属性入口，必须回到上游取得明确取舍，不得仅在 evidence differences 中披露后继续通过。
8. **响应容量预算**：合同记录必答单元、预计首次作答时间、一次重试和教师讨论时间；超过预算时阻止进入实现或要求明确缩减。
9. **候选等级分离**：Schema/导出绿色只能证明 pipeline；教师控制、真实互动和恢复路径通过后，才允许写 `engineering candidate`。

PDF/PPTX 只保留轻量兼容门禁：可以打开、页数正确、主要内容可读、静态状态有意义、差异披露真实。除非具体课例另行要求，不把 PowerPoint 对象级编辑率作为通用 P0。

## 8. 请重点回答的问题
